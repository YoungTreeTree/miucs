# Rapidly 实时人声分析

> 2026-10-26 起默认使用[混音主旋律](predominant-mixture.md)。本文记录保留的人声模式及历史验证。

macOS 可选接入 Rapidly v1.1.0 的 `music-stem-separation-96ms.v1.1.rapidly`，边采集系统声音、边分离人声、边计算音高。只使用名为 `vocals` 的输出，其余五个输出的增益为零。模型内部为单声道，SDK 负责输入声道和采样率转换。

菜单栏「音高来源」可以选择 **人声旋律（Rapidly）**或**混音主旋律**，选择自动保存。状态行显示实际运行来源；没有授权时显示「Rapidly 试用 · 含水印」，加载失败则明确显示音高暂停，音量与起音仍继续更新。切换会重新建立音频会话，不补播旧旋律；键盘监听继续独立运行。

## 授权与本地处理

这是专有 SDK，个人非商用也不自动获得无水印授权。官方提供无 key 的试用运行方式，但会故意降低输出质量；这可能干扰音高判断。没有去除或规避水印，也不能把试用测量当作已授权模型的质量。参见 [SDK 说明](https://github.com/rapidly-labs/rapidly-sdk#licences) 与[完整授权条款](https://github.com/rapidly-labs/rapidly-sdk/blob/a75155656556b38709fe77a706958dcbe1f13624/LICENSE)。

本接入默认使用试用模式，另支持厂商签发的 `lk_` 离线 key。将授权原文保存到本机 `~/Library/Application Support/Miucs/rapidly-license.txt` 后重启；文件不进入仓库或应用包，不在日志中打印。命令行测试也可通过 `MIUCS_RAPIDLY_LICENSE_FILE` 指向该文件。SDK 返回 key 接受成功并不证明它覆盖当前音乐模型；菜单显示「已载入离线授权」，实际模型覆盖范围仍由 SDK 执行。

没有接入 `sk_` 订阅或 `ak_` 激活模式；这样的 key 会在注册前被拒绝，避免启动未配置的在线授权流程。本接入的音频处理在本机完成，不上传音频，不修改系统播放音量，也不播放分离后的人声。

## 构建与验证

```sh
zsh build.sh --rapidly
zsh scripts/test-rapidly.sh
python3 scripts/benchmark-rapidly.py
```

`setup-rapidly.sh` 将官方签名的 XCFramework、音乐模型、LICENSE 和 NOTICE 下载到忽略的 `build/rapidly/`，逐文件检查固定 SHA-256。模型和文本来自 SDK 提交 `a75155656556b38709fe77a706958dcbe1f13624`；XCFramework 使用官方 v1.1.0 发布包及 Swift Package 声明的校验和。构建把 macOS framework、模型和完整授权说明放入本地应用，并完成嵌套签名。不要把这些专有二进制、模型或授权文件提交到源码仓库；向他人分发带 SDK 的应用需要相应授权。

普通 `zsh build.sh` 和现有 Xcode 配置不下载、不链接 SDK，首次启动默认使用混音主旋律；如果在新版来源偏好中手动选择了人声模式而当前包没有 SDK，则提示音高暂停，可在菜单选择混音主旋律。Rapidly 本地试用构建通过上述 CLI 开关启用。应用运行不依赖 Python；Python 只用于离线对照。

基准使用已准备的《童话》混音和人工标注，首次准备见[旋律基准](melody-benchmark.md)。输出为 [Rapidly 对照报告](validation/rapidly-benchmark.json)，SDK 接口与时间对齐检查为 [原生测试](validation/rapidly-vocal-tests.json)。这些歌曲之前已用于评估，不重新宣称为未见样本。

歌声音高模型与门控现已接入，当前实现和前后对比见 [歌声音高识别](singing-pitch.md)。下方旧结果保留作历史基线。

## 分析与时间语义

- `AudioAnalysisPipeline` 仅将分离后 PCM 送给 `SingingPitchAnalyzer`（CREPE Tiny + 有效基频门控），同时提供按原始样本序号对齐的混音能量参考。音量、起音、频谱和立体声特征始终由原始 PCM 计算，数值与关闭分离时一致。五线谱与飞鸟共用人声音高，键盘星爆保持独立。
- 每个采集会话独占一个原生 processor，在串行音频队列处理，模型加载离开主线程。每次向 SDK 提交最多 512 个采样点，及时取走输出，避免在原生队列堆积音频。
- SDK 报告的最大模型延迟为 4608/48000 = **96ms**。输出首样本仍对应原始输入首样本，48kHz 和 44.1kHz 的全部输出相加测试均验证零样本偏移；因此不凭延迟常数修改音高时间戳，也不利用歌曲标注搜索最佳时间偏移。
- 预热时没有音高，原始特征照常发布。音高帧保留原始 PCM 时间，绘制继续按真实帧龄判定过期。音频格式变化会重建 processor，采集重连会创建全新状态。
- 歌声模式下分离或模型失败时清除旧旋律并暂停报音，菜单明确显示暂停状态；不会自动把原始伴奏当成人声；失败不触发整个音频采集反复重连。
- 512 点在 48kHz 下对应约 10.67ms，计算耗时要小于输入间隔才能持续跟上。模型延迟、音高窗口、换音确认及显示延迟是不同量；离线探针不把它们混称为端到端延迟。文件尾的补零只用于有限音频的完整评分，实时捕获不补播或补零。

## 旧频谱音高器结果（2026-10-24）

Apple M4 / 32GB，官方 v1.1.0 framework，完整保留试用水印，使用当前音高分析器。31 段《童话》混音共 230.82 秒，最终复测结果：

| 指标 | 原始混音 | Rapidly 试用人声 |
| --- | ---: | ---: |
| 有基频帧音高命中率（误差 < 50 音分） | 76.94% | 78.84% |
| 无基频区间音高误报率 | 98.91% | 95.59% |
| 八度错误率 | 2.70% | 2.79% |
| 开头 12 音谱面对照，`fdps_2_01` | 7/12 | 6/12 |
| 开头 12 音谱面对照，`geniusturtle_4_01` | 7/12 | 7/12 |

平均有声段命中有小幅提升，但对谱结果没有提升，停顿区误报仍多，个别片段退步。试用模式重复运行有小幅波动（首次全组有声段命中 79.11%，最终复测 78.84%），不能将其作为已授权模型或所有流行音乐的准确率保证。

每批 512 点输入对应 10.67ms，分离加音高分析的各片段 p95 为 **2.74～3.02ms**，最慢一批 **10.84ms**。230.82 秒音频的纯处理累计约 **28.80 秒**，平均速度足够持续跟上输入；最慢块说明这不是硬实时期限保证。统计排除文件解码、系统捕获、主线程、显示与首次模型加载。最新音高窗口中心在交付时约落后 **107～128ms**，首次完整音高结果在累计输入约 **171ms** 后产生；实际屏幕还需加上原有换音确认和动画时间。

已在 `/Applications/Miucs.app` 安装并重启该本地试用构建，生产日志确认启用 Rapidly、48kHz 双声道系统捕获成功。短片段实际回放时看到了音符和旋律轨迹更新。该检查没有录制或导出用户桌面内容；未重新要求实体键盘验收。

## 测量限制

分离结果可能仍包含伴奏、和声和水印；人声分离不等于识别出唯一主唱。无基频区间、八度错误和短错音仍由同一套指标评分。CPU 测量排除文件解码、系统采集、UI、显示和首次加载；报告同时保留每段 p95 与最慢块，不能用平均加速比替代实时稳定性。
